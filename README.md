# JIT Persistent-Memory Agent Prototype

A small proof-of-concept for a **stateless LLM assistant with persistent, just-in-time external memory**.

The central idea is simple:

> The LLM does not carry an ever-growing conversation transcript between interactions. Instead, the system persists what happens externally and retrieves only the context needed for the current task.

This prototype is intentionally small. It is designed to test the architecture, failure modes, and retrieval behavior before adding heavier components such as vector search, rerankers, graph databases, workflow engines, or larger models.

---

## What This Prototype Demonstrates

The current implementation demonstrates:

- **Stateless Primary Agent invocations** — no hidden accumulated chat transcript is automatically carried from one interaction to the next.
- **Append-only persistent event history** in PostgreSQL.
- **Cross-process recall** — the application can be terminated completely and later recover prior information from persistent storage.
- **Cross-conversation recall** — conversation IDs organize history but do not act as hard memory boundaries.
- **Just-in-time retrieval** — the Primary Agent retrieves bounded historical context only when it decides earlier information is required.
- **Structured LLM decisions** validated with Pydantic.
- **Deterministic metadata** — IDs, timestamps, sequence numbers, scope, retrieval limits, and other system-known values are generated by application code rather than by the LLM.
- **Exact provenance** — retrieval results preserve the source event IDs and ordering metadata used to generate an answer.
- **Deterministic temporal reasoning support** through per-conversation and global sequence numbers.
- **Persistent error events** for recoverable orchestration failures.
- **Local inference** through Ollama.
- **Local PostgreSQL** with no Docker or remote database dependency.
- **A dedicated disposable test database** so the development event history can remain append-only while tests stay deterministic.

The prototype deliberately uses PostgreSQL full-text search before introducing embedding/vector retrieval.

## Core Architecture

```text
Current user input
        |
        v
Persist USER_PROMPT
        |
        v
Fresh Primary Agent classification
        |
        +------------------------------+
        |                              |
        | RESPOND_DIRECTLY             | RETRIEVE_CONTEXT
        |                              |
        |                              v
        |                    Persist RETRIEVAL_REQUEST
        |                              |
        |                              v
        |                    PostgreSQL retrieval
        |                              |
        |                              v
        |                    Persist RETRIEVAL_RESULT
        |                              |
        +---------------+--------------+
                        |
                        v
                 LLM response
                        |
                        v
              Persist AGENT_RESPONSE
                        |
                        v
            Discard temporary LLM context
```

The next external interaction starts fresh.

The continuity comes from persisted history and retrieval, not from an accumulated in-memory LLM transcript.

## Design Principles

### Persistent experience without persistent LLM context

The system should be able to accumulate a large external history without requiring each new inference to ingest that entire history.

Historical growth should primarily become a **storage and retrieval problem**, not a continually growing inference-context problem.

### Persist first, interpret later

Raw interactions and meaningful system events are retained as the authoritative history.

The prototype does **not** use an LLM-controlled `memory_assertion`, `remember_this`, or similar gate. Persistence is application behavior, not an LLM decision.

### Deterministic code owns deterministic information

The LLM currently decides only:

```text
RESPOND_DIRECTLY
```

or:

```text
RETRIEVE_CONTEXT
query_text: <what information is needed>
```

Application code supplies retrieval scope, event-type filters, ordering, limits, IDs, timestamps, and sequencing.

### Retrieval technique is not the Primary Agent's concern

The Primary Agent describes what context it needs.

The Retrieval Service decides how to find it.

Today that means PostgreSQL metadata filtering and full-text search. A future implementation can add vector similarity or reranking behind the same conceptual boundary.

## Event Model

The append-only event log currently supports:

- `USER_PROMPT`
- `AGENT_DECISION`
- `RETRIEVAL_REQUEST`
- `RETRIEVAL_RESULT`
- `AGENT_RESPONSE`
- `SYSTEM_EVENT`
- `ERROR`

Each persisted event includes deterministic metadata such as:

- `event_id`
- `conversation_id`
- `correlation_id`
- `global_seq`
- `conversation_seq`
- `event_type`
- `source`
- `created_at`
- structured JSON payload
- schema version

### Two ordering systems

The prototype maintains two explicit sequence values:

- `conversation_seq` — authoritative event order **within one conversation**
- `global_seq` — authoritative event order **across all conversations**

This avoids requiring the LLM to infer event ordering from nearly identical timestamps.

## Retrieval

The current Retrieval Service can use:

- conversation scope
- event/source type filters
- chronological ordering
- relevance ordering
- result limits
- PostgreSQL full-text search

Normal Primary Agent retrieval currently searches persisted:

- `USER_PROMPT`
- `AGENT_RESPONSE`

across conversations by default.

Other event classes are persisted for provenance and debugging but are not yet automatically included in ordinary conversational retrieval.

### Current retrieval behavior

When a free-text context query exists, application policy uses relevance ordering.

When there is no free-text query, it uses reverse chronological ordering.

The current prompt is excluded from its own historical retrieval using deterministic sequence cutoffs:

- `conversation_seq` for current-conversation retrieval
- `global_seq` for all-conversation retrieval

## Current LLM Backend

The prototype uses a local Ollama model through a small swappable `LLMClient` interface.

The model is configured through the environment rather than hardcoded into the architecture.

The current implementation:

- explicitly disables thinking in Ollama requests;
- uses Ollama JSON-schema-constrained output for the classification step;
- validates structured output with Pydantic;
- bounds classification generation to 64 tokens;
- bounds response generation to 256 tokens;
- logs Ollama timing/token telemetry for diagnosis.

The project has been tested successfully with a quantized Qwen3 4B instruct model on a Windows laptop with:

- quad-core Intel Core i5 with Hyper-Threading
- 16 GB system RAM
- NVMe SSD
- Intel integrated graphics
- no dedicated GPU

No GPU is required for PostgreSQL. Local LLM inference is CPU-bound on this hardware.

## Installation

### 1. Clone or open the repository

```powershell
cd path\to\jit_agent_prototype
```

### 2. Install Python dependencies

```powershell
uv sync
```

### 3. Install and start PostgreSQL

Install PostgreSQL natively on Windows and ensure the PostgreSQL service is running.

Create a development database and role appropriate for your local environment.

Apply the schema:

```powershell
psql -d jit_agent -f schema.sql
```

The exact connection string is configured through `DATABASE_URL`.

### 4. Install and start Ollama

Install Ollama, start its local service, and pull a suitable small instruct model.

For example, use the model configured in your local environment.

### 5. Configure environment variables

Create a local `.env` file.

Example:

```dotenv
DATABASE_URL=postgresql://USER:PASSWORD@localhost:5432/jit_agent
OLLAMA_BASE_URL=http://localhost:11434
OLLAMA_MODEL=<your-local-instruct-model>
```

`.env` is ignored by Git and should not be committed.

## Running the Agent

### Interactive REPL

```powershell
uv run jit-agent
```

The CLI prints a `conversation_id`.

Example:

```text
conversation_id: <uuid>
Type 'exit' or 'quit' to stop.
> hello
...
```

You can resume a known conversation:

```powershell
uv run jit-agent --conversation-id <uuid>
```

### Single-shot mode

The CLI also supports one interaction per process:

```powershell
uv run jit-agent --once "What did I tell you about Project Falcon?" --conversation-id <uuid>
```

This mode is useful for scripting and for proving that recall does not depend on Python process state.

## Proof-of-Concept Recall Example

A useful demonstration is:

### Process A

```text
User:
The codename for Project Falcon is Blue Cedar.
```

The prompt and response are persisted.

Terminate the process completely.

### Process B

Start a fresh process and ask:

```text
What codename did I give Project Falcon?
```

The Primary Agent starts without the previous transcript, recognizes that historical context is required, queries persisted history, receives only relevant events, and answers from those events.

The project also includes an automated **cross-conversation, cross-process** memory test, demonstrating that recall is not dependent on reopening the exact same Python process or conversation.

## Diagnostic and Benchmark Scripts

### Ollama diagnostics

```powershell
uv run python scripts/diagnose_ollama.py
```

Used to isolate:

- model loading latency
- prompt-evaluation latency
- generation latency
- structured-output overhead
- token counts
- response timing

### Scale test

```powershell
uv run python scripts/scale_test.py
```

A previous benchmark inserted increasing amounts of unrelated historical noise and then performed a real end-to-end retrieval.

Observed prototype results:

| Noise events | Items returned | Target found | Retrieved content | Latency |
|---:|---:|:---:|---:|---:|
| 500 | 1 | Yes | 45 chars | ~8.7 s |
| 2,000 | 1 | Yes | 45 chars | ~7.8 s |
| 5,000 | 1 | Yes | 45 chars | ~7.9 s |

At this scale and with non-adversarial noise, stored history increased 10x while the context returned to the LLM remained constant.

This is evidence for the intended **just-in-time context** property; it is not a claim about million-event production scale.

### Adversarial benchmark

```powershell
uv run python scripts/adversarial_benchmark.py
```

The benchmark probes:

- high lexical overlap
- closely related entity names
- conflicting facts over time
- current vs. original vs. immediately previous values

The temporal cases exposed an early failure in which retrieved facts had been flattened without explicit ordering metadata.

The fix was not a larger model or a new retrieval system. The existing deterministic `conversation_seq` was exposed to the LLM as the authoritative ordering signal.

The benchmark subsequently passed all five cases in the measured run:

| Case | Correct target rank | Result |
|---|---:|:---:|
| High lexical overlap | 0 / 5 | Pass |
| Closely related entities | 2 / 3 | Pass |
| Temporal: current | 0 / 3 | Pass |
| Temporal: original | 2 / 3 | Pass |
| Temporal: immediately previous | 1 / 3 | Pass |

This illustrates an important design principle of the project: **preserve useful deterministic structure before adding more model complexity.**

## Known Limitations

This is a prototype, not a production memory system.

### Full-text search is lexical, not semantic

Current PostgreSQL retrieval depends on shared vocabulary.

For example, a stored statement such as:

```text
The codename for Project Falcon is Blue Cedar.
```

can be found reliably by a query containing terms such as `Falcon`, `codename`, or related shared words.

A fully paraphrased request such as:

```text
What was that tree-related name for the bird initiative?
```

may fail because there is no lexical overlap.

The repository intentionally includes tests documenting this failure boundary.

This is the primary evidence-based justification for a future semantic retrieval layer such as `pgvector`.

### OR-based full-text retrieval favors recall over precision

The current FTS query logic ORs query terms.

This makes retrieval tolerant of extra paraphrased words but can allow generic shared words to produce unrelated candidates.

### Retrieval does not yet search every internal event class automatically

All meaningful event types are persisted, but ordinary Primary Agent context retrieval currently defaults to user prompts and agent responses.

Internal events such as retrieval traces and errors remain in the authoritative history and can be queried programmatically, but a future retrieval policy should make them available when a user's request specifically calls for them.

### Inference provenance is not yet fully persisted

Ollama runtime telemetry is logged, but model name, prompt-template version, generation parameters, token counts, and timing information are not yet represented as a complete authoritative inference-event history.

### English full-text configuration

The current PostgreSQL text search uses the `english` text-search configuration.

### Local CPU inference latency

A 4B model on this hardware is usable for a prototype but not low-latency production inference.

Some real interactions take multiple seconds because a retrieval interaction involves a classification inference followed by a response inference.

---

## Why pgvector Is Not Implemented Yet

Semantic retrieval is an obvious future capability, but it was deliberately deferred.

The project first established that:

- persistence works;
- stateless recall works;
- cross-process recall works;
- cross-conversation recall works;
- context remains bounded under tested history growth;
- deterministic temporal structure works;
- lexical retrieval has a documented, reproducible failure boundary.

The next semantic-retrieval phase can therefore be evaluated against a known working baseline rather than being added speculatively.

The expected direction is a hybrid retrieval layer:

```text
metadata filtering
        +
PostgreSQL full-text search
        +
pgvector semantic similarity
        |
        v
candidate fusion/ranking
        |
        v
bounded context
```

A reranker should only be added if benchmarking demonstrates that hybrid candidate ordering remains inadequate.

## Next Likely Phase

The next major capability to evaluate is **hybrid semantic retrieval with PostgreSQL + pgvector**, while preserving the existing full-text and metadata retrieval paths.

The current FTS failure corpus should remain unchanged and serve as a control group.

The semantic layer should only be considered successful if it:

1. recovers the documented zero-vocabulary paraphrase failures;
2. preserves exact and temporal retrieval behavior;
3. keeps returned context bounded;
4. does not materially increase false positives;
5. retains exact provenance back to authoritative source events.

---

## Philosophy

This project favors:

- empirical testing over speculative infrastructure;
- deterministic structure over LLM inference when possible;
- minimal LLM-generated control data;
- preserved provenance;
- bounded context;
- small, inspectable modules;
- one component per demonstrated need.

When a failure can be fixed by exposing information the system already knows deterministically, that is preferred over using a larger model or adding another AI subsystem.
